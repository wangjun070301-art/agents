# P14：崩溃耗尽之后进入 BLOCKED

## 这一轮补什么

P13 让崩溃可以重试。但重试也耗尽之后，调度器只是返回失败，
阶段原地不动，调用方拿到一个 `{ok:false}` 就没有下文了。

真实工作流需要的是：**反复崩溃的任务应该停下来等人看一眼**，
不是无限重试，也不是静默丢弃。

## 设计

SchedulerOptions 新增 `blockOnExhaustion`（默认 false）：

| 失败类型 | 耗尽后 | 理由 |
|---|---|---|
| 可重试故障（信号杀） | **进 BLOCKED** | 外部故障反复出现，需要人工介入 |
| 不可重试（超时/取消） | 留在原地 | 是决策，不是故障；冻结整条流水线是错的 |
| 门禁拒绝 | 留在原地 | 已有重试逻辑，不是环境问题 |

## 过程中发现的真 bug

第一次实现时，阻塞代码写在了循环外的公共失败路径上，
但 `catch` 里对最后一次适配器错误**直接 return 了**：

```ts
} catch (error) {
  ...
  this.persistFailure(failure);
  return { ok: false, attempts, failure };   // ← 绕过了阻塞逻辑
}
```

结果：门禁耗尽能阻塞，适配器崩溃不能。

**修法**：抽出 `finishFailure()`，两条失败路径都走它。
这是"单一出口"的价值——阻塞策略不可能被某条路径绕过。

## 测试（新增 5 项）

| 检查 | 结果 |
|---|---|
| 可重试故障耗尽 → 进 BLOCKED | 通过 |
| 不可重试故障 → 不进 BLOCKED | 通过 |
| 默认不开阻塞 | 通过 |
| BLOCKED 后可命名原阶段恢复 | 通过 |
| 终态不能进 BLOCKED | 通过 |

## 结果

```
test/workflow-recovery.test.ts   15/15
全量                              359 用例，341 通过，18 失败（基线）
```

## 这一轮证明了什么

1. 崩溃耗尽后能进入 BLOCKED，并且记录阻塞发生在哪个阶段
2. 超时和取消不会误触发阻塞
3. BLOCKED 可以按协议恢复
4. 阻塞策略不会被某条失败路径绕过（单出口）

## 这一轮证明不了什么

1. 阻塞之后由谁恢复、多久恢复，没有定义。现在只有协议层面的
   "可以恢复"，没有运营层面的"何时恢复"。
2. 多任务计划里，一个任务阻塞后其余任务怎么处理没测。
   runPlan 目前不看 pipeline 的 BLOCKED 状态。
3. 阻塞状态没有持久化到 stateDir。Pipeline.history 在内存里。
4. 没有"人工解除阻塞"的入口。只能靠调用方自己调 advance。
