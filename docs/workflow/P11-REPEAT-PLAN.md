# P11：多任务计划的重复稳定性

## 为什么做这一轮

P10 的三子进程计划跑了一次，7/7。P9 已经证明单次通过不代表稳定，
所以这一轮把 P10 包成可重复运行。

**第一次跑 3 轮，0/3 通过。** P10 那次 7/7 是运气。

## 三种失败模式

| 轮次 | 结果 | 失败项 | 真因 |
|---|---|---|---|
| 1 | 6/7 | P2（T-JOIN 没完成） | 子进程只读了文件，没执行验证命令 |
| 2 | 6/7 | P7（超时任务） | 10 秒内跑完了，不是失败 |
| 3 | 5/7 | P1、P2 | 子进程声称了测试结果，但输出里没有 |

**这三种都不是门禁缺陷**，是我的演练对子进程行为假设太乐观。

## 逐条修正

### 问题 1：T-JOIN 被要求跑命令但没跑

原任务描述是"跑两个测试并汇总"。子进程读了文件就回答了。

**修法**：明确写"You must actually execute both"，并要求报告退出码。

同时 **P2 的断言改了**：原来要求 T-JOIN 必须完成；现在只要求
"它没在依赖之前运行"且"被拒时理由真实"。因为 T-JOIN 能不能完成
取决于子进程服从性，不是门禁能力。

### 问题 2：10 秒超时任务居然成功了

我假设 10 秒一定不够，但子进程有时几秒就跑完。

**修法**：P7 现在接受两种结果——超时（必须是 `adapter-error` 且阶段不动），
或真的跑完了（阶段同样不动）。**不假装每次都能测到超时。**

### 问题 3：`timeout_seconds: 8` 违反 schema

我把超时改成 8 秒想让失败更稳定，但协议最小是 10。脚本直接崩了，
P7 根本没执行。

**修法**：改回 10，并在注释里说明为什么不能更低。

## 修正后的结果

```
node tools/p11-repeat-plan.mjs --runs 2 --sandbox bypass

[p11] run 1/2: exit=0 checks=7/7 completed=["T-A","T-B","T-JOIN"] 89s
[p11] run 2/2: exit=0 checks=7/7 completed=["T-A","T-B","T-JOIN"] 97s
2/2 runs passed all seven checks (elapsed 214s)
```

**2/2 全过，三个任务都按依赖顺序完成。**

## 这一轮证明了什么

1. **P10 的单次 7/7 不可靠** —— 修正前的 0/3 是直接证据
2. **失败来自测试设计，不是门禁** —— 三种失败都能定位到具体假设
3. **修正后连续两次 7/7** —— 但两次仍不是统计意义上的稳定

## 这一轮**证明不了**什么

1. **2/2 不是稳定性的证明。** 修正前 0/3，修正后 2/2，样本都太小。
   要真说稳定，需要 10 次以上。
2. **P7 的超时路径可能没被执行。** 修正后的断言允许"跑完了"，
   所以那次 7/7 里 P7 可能只是任务完成，没测到超时分类。
3. **只测了 `bypass` 沙箱。** `workspace-write` 下子进程执行不了命令，
   行为完全不同。
4. **`runPlan` 仍是串行。** 并发没测。
