# P7：调度器

## 解决的问题

P6 结束时，四块零件各自能用，但没有东西把它们串起来：

```
CodexAdapter  →  能执行
observer      →  能观测
test-output   →  能解析
Pipeline      →  能判门禁
```

缺的是**决策者**：谁调谁、按什么顺序、被拒了怎么办。

## 交付内容

| 文件 | 作用 |
|---|---|
| `src/workflow/scheduler.ts` | `Scheduler`：执行、采证、判定、持久化 |
| `test/workflow-scheduler.test.ts` | 12 项单元测试 |
| `tools/p7-e2e.mjs` | 真实子进程端到端演练（7 项检查） |

## 一个关键设计修正

第一版 `runTask` 让每个任务自己推进阶段，测试立刻暴露问题：

> 任务 B 依赖任务 A，但 A 已经把阶段从 PLAN 推到 DISPATCH，
> B 再想推 DISPATCH 就是非法转换。

**根本错误**：阶段是**整体**的属性，不是单个任务的。三个任务在 DISPATCH 下派工，
阶段只移动一次，等三个都完成、门禁看到合并证据时才移动。

修正后职责分明：

| 方法 | 做什么 | 不动阶段 |
|---|---|---|
| `runTask(envelope)` | 执行一个任务，采证，判断该任务自身证据是否自洽 | ✓ |
| `advanceStage(to, state)` | 评估门禁，通过才移动 | ✗ |
| `runPlan(tasks)` | 按依赖顺序跑完所有任务 | ✓ |

这样"任务完成"和"阶段通过"是两个独立事实，不会被一个任务绑架。

## 每任务的自洽判定

`runTask` 不问门禁，只问一个问题：**这个任务的证据支持它自己的声明吗？**

四项检查，任一不过就返工：

1. `validateTaskResult` —— 结果与信封对账
2. `claimIsSupported` —— 成功声明有证据
3. 转录分歧 —— 声明被自己的命令输出打脸
4. 观测对账 —— 声明的文件清单与磁盘实际改动不符

返工时走 `adapter.resume`，把拒绝理由作为反馈，不是重新派一次。

## 持久化

`stateDir` 下每个任务一个目录：

```
stateDir/tasks/T-1/attempt-1.json
stateDir/tasks/T-1/attempt-2.json
stateDir/tasks/T-1/failure.json   （只在最终失败时写）
```

重启后能看清"试了几次、每次为什么被拒"。

## 真实端到端结果

```
node tools/p7-e2e.mjs --sandbox bypass
exit=0, 7/7
```

链路：真 git 仓库 → 真 `codex exec` 子进程 → 观测 → 门禁 → 阶段前进。

| 检查 | 结果 |
|---|---|
| S1 任务完成无拒绝 | 1 次通过 |
| S2 任务运行不动阶段 | 阶段仍是 IMPLEMENT |
| S3 观测到真实改动 | `["src/greet.js"]` |
| S4 尝试记录落盘 | `attempt-1.json` 存在 |
| S5 G2 放行真实证据 | 阶段变 REVIEW |
| S6 门禁记录进历史 | `passedGates=["G2"]` |
| S7 同一套线拒绝虚假声明 | `reported but unchanged: src/never-touched.js` |

## 过程中修掉的两个真问题

**问题 1：重试时观测基线错位。**

第一次尝试改了文件但被拒（测试输出不合格式），第二次尝试发现文件已改，
不再改动，于是观测报"零变化"，看起来像什么都没做。

修法：重试复用**第一次尝试的基线快照**，而不是每次重新拍。这样
"第一次做了、第二次确认"不会被误判成"两次都没做"。

**问题 2：`ok` 不是测试结果。**

子进程跑 `node src/greet.test.js`（普通脚本，只打印 `ok`），
却报告了一条 `passed` 测试。解析器正确地拒绝了——`ok` 不是任何
已知测试框架的输出格式。

这不是解析器的 bug，是**演练任务写错了**：应该让它跑 `node --test`，
那才会产出真 TAP 输出。改任务描述后通过。

**这条值得记住**：子进程会把"脚本退出码 0"当成"测试通过"。
解析器守住这个边界，正是它存在的理由。

## 这套演练证明了什么

1. 四块零件真的能串起来，不是各自孤立的单元。
2. 观测结果和子进程声明是两条独立来源，可以矛盾。
3. 门禁通过是**有记录的**，不是口头声明。
4. 同一套线既能放行诚实结果，也能拒绝虚假声明。

## 这套演练**证明不了**什么

1. **只跑了一次。** 子进程行为有随机性，单次通过不代表稳定。
2. **只覆盖一个阶段。** 从 IMPLEMENT 到 REVIEW（G2），其他五道门禁
   没有在真实链路上跑过。
3. **`runPlan` 没在真实链路里跑。** 只跑了单任务。
4. **没有人工验收环节。** G5 需要真人签收，演练里没有。
5. **失败恢复没测。** 子进程崩溃、超时、BLOCKED 之后的恢复路径。
