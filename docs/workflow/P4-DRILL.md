# P4：门禁实弹演练

## 目的

P3 交付了六道门禁的判定逻辑，但"单元测试通过"只证明每条规则能单独工作。
这一轮要回答一个不同的问题：**门禁真的能拦住坏活吗？**

方法：构造十五个场景，每个喂给 `evaluateAllGates`，断言哪几道门禁必须拦。
其中十二个是坏活，三个是"不该拦"的对照。

脚本：`tools/p4-drill.mjs`，退出码 = 全部符合预期 ? 0 : 1。

## 场景表

| 编号 | 场景 | 期望拦截 |
|---|---|---|
| S0 | 诚实交付 | 无（必须全过） |
| S0b | 已解决的 Major + 未解决的 Minor | 无 |
| S0c | 用绝对路径报告改动 | 无 |
| S1 | 声称成功但没跑任何命令、没有测试 | G2 |
| S2 | 改了 `allowed_paths` 之外的文件 | G2 |
| S3 | 改了文件但没报告 | G2 |
| S4 | 审查留了未解决的 Blocker | G3 |
| S5 | 有一条 AC 未验证 | G4、G5 |
| S6 | 通过但证据是 `n/a` | G4、G5 |
| S7 | 验收时间早于验证时间 | G5 |
| S8 | 验收点名了另一个构建 | G5 |
| S9 | 只签收了一部分 AC | G5 |
| S10 | 两个并行任务共享写路径 | G1 |
| S11 | 依赖成环 | G1 |
| S12 | 有一条 AC 没有任务认领 | G1 |

## 断言的严格性

第一版断言只检查"期望的门禁在拦截列表里"。自查时发现这不够：
S5 期望 `G4,G5`，但实际 `G1` 也拦了（场景里没给全 tasks），
旧断言照样通过。

现在改成：**多拦一个门禁也算失败**。只有显式声明为"必然继承"的门禁
（G5 继承 G4）可以额外出现在列表里。

这条改动让演练从"证明能拦"变成"证明拦在对的地方"。

## 结果

```
node tools/p4-drill.mjs
15/15 scenarios behaved as required
exit=0
```

## 这套演练证明了什么

1. 门禁在缺证据时**不通过**，不是靠默认值放行。
2. 每类坏活**落在正确的门禁**，不是笼统地全挂。
3. 合法但少见的形式（已解决的 Major、绝对路径）**不被误伤**。

## 这套演练证明不了什么

1. **它不能证明门禁在真实项目里拦得住。** 所有场景的输入是我构造的，
   真实开发中的坏活形态比这十二种复杂。
2. **它不能证明证据是真的。** `changedFiles`、`reviewFindings`、
   `verifications` 都是调用方提供的，演练只验证"门禁对这些数据的判断是否正确"，
   不验证数据本身的真伪。真实链路里需要适配器从实际工作区采集这些数据。
3. **它没有覆盖跨任务的一致性。** 比如两个任务各自声称改了同一个文件、
   各自都有证据，但整体状态冲突。
4. **它没有覆盖 BLOCKED 的恢复路径。** 门禁只判断"能不能前进"，
   不判断"卡住之后怎么回来"。

## 下一步（P5 建议）

把演练从"构造输入"推进到"真实输入"：

1. 建一个夹具仓库（两三个文件、两个测试）。
2. 让 `CodexAdapter` 真跑一个任务，从实际工作区采集 `changedFiles`。
3. 故意让子进程做一个不该做的事（改 allowlist 外的文件），
   看采集到的数据能不能让 G2 拦住。

这一步才能回答"端到端能不能拦"。
