# P15：计划跑到一半被阻塞就停

## 这一轮补什么

P14 让崩溃耗尽之后进 BLOCKED。但 `runPlan` 根本不看 BLOCKED：
一个任务把流水线阻塞了，后面的任务照样一个个派出去。

那不是"继续工作"，那是拿没人验收的成果继续叠。

## 设计

`runPlan` 在两个位置检查 `pipeline.isBlocked`：

| 位置 | 为什么 |
|---|---|
| 每轮循环开头 | 上一批任务可能已经阻塞了，剩下的一个都不该跑 |
| 同一批任务之间 | 一批里的第一个任务就可能阻塞，同批的其余任务必须停在它之后 |

被跳过的任务不是静默丢弃，每一条都带原因：

```
pipeline blocked; waiting for a human
```

## 测试（新增 2 项）

| 检查 | 结果 |
|---|---|
| 第一个任务阻塞后，只剩它被调用（`calls.length === 1`） | 通过 |
| 未阻塞时计划正常跑完三项，无跳过 | 通过 |

第二条是防回归：加检查不能把正常路径一起挡掉。

## 这一轮证明了什么

1. 阻塞是整条计划的停止信号，不是单个任务的失败
2. 同批任务也不会越过阻塞点
3. 跳过有原因，不是无声消失

## 这一轮证明不了什么

1. 阻塞之后由谁放行、多久放行——协议上可以，运营上仍没定义
2. 阻塞发生在批次中间时，已派出的子进程不会被召回；只能等它自己结束
